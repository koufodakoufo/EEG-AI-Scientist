## 3. 机器和仓库分别负责什么

| 位置 | 建议角色 | 主要保存内容 |
| --- | --- | --- |
| Windows 电脑 | 本地开发、轻量测试、论文与方案整理，以及远程操作界面 | 活跃代码工作副本、个人环境、研究资料与归档 |
| nccserver0 | 远程开发与需要服务器环境的运行 | 同一框架仓库的远端工作副本、独立 Python 环境、Codex CLI、driver、运行结果 |
| GitHub 或团队 Git 服务 | 代码版本交换与评审 | 源码、配置模板、依赖声明、测试、短报告 |
| 火山云 | 后续团队计算与集成环境 | 团队确认后的工作副本、数据/权重挂载、运行环境 |
| 数据盘或对象存储 | 大文件与研究数据 | 原始数据、权重、大型 checkpoint 和日志 |

Git 不会同步 Python 环境、登录状态、正在运行的进程或训练进度。数据、权重、缓存和大产物另行管理；Git 里记录其版本、校验值和读取方式。

Windows 与 server0 可以持有同一个仓库的两个活跃工作副本。按当前任务决定在哪边编辑和测试，已提交代码通过同一个 GitHub 或团队 remote 交换。push/pull 不会实时同步未提交修改；两边的 Python 环境分别配置。

本地窗口编辑 X: 盘文件时，改的是本机副本，需要提交并同步后远端才能看到。VS Code Remote SSH 窗口编辑远程文件时，直接改 server0 副本，这次编辑本身不经过 GitHub。GitHub 负责版本交换，不是 SSH 操作的中转站。当前服务器适配适合在远端做，本地仍可随时承担代码和任务开发。

同一个运行目录不要同时由两个交互 Agent 或两个 driver 修改。运行中的实验应使用固定代码快照；不要在训练运行目录中随手拉取新版本。

## 4. 用户如何参与 Codex 和服务器操作

推荐先沿用熟悉的路径：

1. 在 Windows 上确认已有 SSH 别名 `nccserver0` 可以连接。
2. VS Code 使用 Remote SSH 连接该主机。
3. 打开 server0 上用户自己的项目目录。
4. 在这个远程窗口中新建终端。
5. 终端中启动服务器上的 `codex`，让它读取交接文档并执行有界任务。

SSH 是 Secure Shell；CLI 是 Command-Line Interface。Codex CLI 是安装在服务器用户环境中的可执行程序，所在位置由安装方式决定，不是项目必须自带的 Python 文件。Shell 通过 `PATH` 找到它；进入哪个项目目录启动，决定它首先面对哪个工作目录。

以下只用于解释操作位置，安装路径须现场检查：

```bash
hostname
pwd
command -v codex
codex --version
codex login status
codex
```

`hostname` 显示机器名；`pwd` 是 print working directory；`command -v` 查询命令解析到的位置，`-v` 使用 POSIX 的短信息形式而不是这里所谓的 verbose；`--version` 显示版本。CLI 启动命令本身没有缩写参数。

人的参与方式：

| 阶段 | 用户负责 | Codex 可负责 |
| --- | --- | --- |
| 初次连接 | 校园网/VPN、已有 SSH 身份、浏览器账户认证 | 检查路径、权限、磁盘、依赖、联网 |
| 配置 | 看清目标机器和目录，完成需要本人登录的界面 | 准备独立目录和环境、最小适配、执行短测试 |
| 日常开发 | 确定研究问题、解释结果、审阅关键改动 | 写代码、调试、整理证据、执行限定实验 |
| 自动研究 | 审阅 brief、设置资源预算与重要边界 | driver 启动 Agent，会话间通过文件交接 |

`codex` 的交互会话适合用户观察和指导；框架 driver 使用 `codex exec` 做非交互运行，exec 指 execute。二者不是必须同时运行的两份研究控制器。

## 8. local、TiONE 与火山云

local 是相对于“运行 eegfm 的机器”：

- 在 Windows/WSL 启动：本机执行。
- 在 server0 启动：server0 执行。
- 在火山云实例启动：火山云实例执行。

当前本地后端基于 Linux 风格后台进程；用户 Windows 原生兼容性没有验证，需要时优先考虑 WSL。WSL 是 Windows Subsystem for Linux。无 GPU 合成任务可以在个人电脑上做，但本轮目标仍是 server0 部署。

TiONE 是该项目的腾讯云训练提交后端，tikit 是其延迟加载依赖；它们不是“所有服务器都要安装”的基础组件。server0 上用 local 不需要腾讯云密钥。火山云若直接使用虚拟机，可以用 local；若用平台任务队列，应实现或采用火山云对应后端；若团队提供其他调度器，则接它。具体平台形态尚待确认。

local 当前不会分配 GPU 或排队。REVE 旧配置是六个分片、每个申请六张 GPU，方法内部又要求至少五张可见 GPU。因此不能只把 backend 改成 local，或把 gpus_per_job 改成 1 就认为迁移成功。

火山云建议共享的是基础镜像、只读数据/权重和协作代码；个人工作副本、虚拟环境、run 输出与 Codex 身份应可区分。团队如果只提供共同账户，仍应约定独立目录和写入边界，不能默认在知非正在运行的目录中直接修改。

迁移到火山云后，server0 仍可做开发、小实验和回归检查。无需保持两台机器的全部数据同步，也不需要现在搭跨云调度系统。

## 10. 原框架机制和旧审查边界

两张用户截图应理解为不同层次：

- 实验运行图描述 bin/eegfm、local/TiONE、状态、driver、Agent 与人工 brief 的协作。
- NeuroTaste 图描述研究方向：Paper-to-Bench 与实验工具提供任务和证据，Agent 做科研决策，skills 从经验中提炼，并在新问题上检验改善。

截图中的能力框图不是所有能力已验证的证明。

关键概念：

| 概念 | 含义 |
| --- | --- |
| Run | 一次完整研究运行 |
| Attempt | 带编号、提案、代码快照和评估结果的一次尝试 |
| Job | 后台真正执行命令的计算作业 |
| Agent session | driver 启动的一次 Codex/Claude 会话 |

一个 attempt 可对应多个数据集作业，也可跨会话；一个会话可以处理多个 attempts。旧示例使用 A1、A2 等编号。

旧快照实际流程是“driver 等待、Agent collect”：driver 轮询登记的 job IDs，作业终态后启动新会话，Agent 调用 eval collect、分析并继续。collect 独立不等于要用户手工执行；但完整 job 列表与 collect 动作仍依赖 Agent 遵守协议。

driver 每次启动新的 codex exec，主要通过文件续接，不自动恢复完整聊天。后台 driver 不是已有系统服务管理器；停止 driver、Agent、训练是不同操作。进程恢复不等于训练 checkpoint 恢复。

前一轮旧快照审查指出：

- 冻结前禁止 baseline/iteration；validation 检查快照和允许修改范围；test 前须锁候选。
- test 指标顶层键名检查不是全面泄漏检测；测试集也没有操作系统级权限隔离。
- 读全部文件、更新 NOTES 等部分要求为提示词协议。
- 人工审批命令同一账户也能调用，actor 写 human 不能证明真人授权。
- GPU 小时、max_attempts 与 done 所需产物没有完整硬拦截。
- 已登记等待作业的恢复测试通过，不代表提交接受后落账前中断也安全；旧实现可留下 submitting 并在重试生成新 job ID。
- test 使用既有 attempt/code，不能声称重新完成与 validation 相同的全部哈希校验。

这些点应按目标排序：第一轮仅修阻挡轻量部署的适配；重要故障恢复与资源边界在准备长期运行前处理；不要先开展无边界框架重写。

## 12. 阶段 B 从任务构建到技能迁移

### 12.1 为什么选 BrainPEC 与一个目标发现

BrainPEC 是团队提出论文线索的高度匹配候选；用它是因为其问题、数据/模型、实验和结论可作为首个任务来源，不是因为用户的研究贡献被限定为复现这篇论文。

FIRE-Bench 第 3.1 节从核心图表选目标实验叶节点，再把其父问题作为题面，给定范围和评价标准，隐藏具体实施与结论。我们的“一个明确结论”指构建者有可核验的评分依据，不是把这句话当答案给受测 Agent。

第一项工作是建立这套任务构建和测量方法在 EEG FM 上的实例。资源允许后可扩展到其他论文或新的研究问题；大范围 scientific taste 与自主选题能力不能由一个被指定的问题证明。

### 12.2 三种工作必须分别标注

| 工作 | 执行者看到什么 | 目的与结论 |
| --- | --- | --- |
| 参考路径验证 | 构建者/工程 Codex 可读完整论文、代码和目标结果 | 证明实验有条件执行，核实参考结论与评分；不是独立发现 |
| 受约束重新发现 | 受测 Agent 只得父问题、资源、预算和中性评价要求 | 检查它能否自主提出假设、选实验、执行并形成证据支持的结论 |
| 技能迁移比较 | 新鲜的两个受测会话看到同一预留任务，只有 skill 条件不同 | 检查经验是否改变新问题上的研究决策与表现 |

构建者可以用我们当前会话读论文。当前会话已经看到方法和结论，不能接着直接当“未看答案”的基线 Agent。重新发现运行必须建立新的会话和限定材料范围，不继承本交接全文、参考论文、评分答案或已含答案的共享记忆。

### 12.3 具体步骤与文件产物

这些文件名是建议，不代表已经创建；实现时应放在团队同意的任务/文档目录中。

| 步骤 | 动作 | 完成证据 |
| --- | --- | --- |
| B1 论文到问题树 | 读 BrainPEC 正文与附录，提取根问题、子问题、假设、实验和发现；保留每条与章节/图表的对应 | research_tree.json 与人工核对记录 |
| B2 选择和封存 | 选择一个有实证锚点且资源可用的开发任务 T_dev；同时指定预留小任务 T_holdout 或其选择规则 | TASK_PUBLIC.md、resource_manifest、构建者私有参考包、预留任务清单 |
| B3 验证与最小接入 | 用可信参考实现验证数据、checkpoint、指标和可复现性；接到 wzf 的状态与作业接口 | reference_check、输入/输出契约、少量运行证据 |

### 12.4 一个题面的示例

下面是示例措辞，不是已定实验或已验证的细粒度结论：

“在指定 EEG 模型和临床任务中，频域相关信息在不同表征层中如何分布？设计能够检验这一问题的实验，说明结果支持哪些结论、还不能支持哪些结论。”

给受测 Agent：数据和模型入口、采样与通道说明、预算、输出/证据要求，以及允许使用的通用工具。
不给受测 Agent：BrainPEC 的逐层 ridge 方案、目标图、预期趋势、作者结论和可直接跑出答案的完整审计脚本。

最终题面必须从所选图表结论的父问题导出。不要先随便选 alpha 功率再把它说成论文已报告的某个结果；也不要把问题缩成“按指定方法算某个数”，这样会失去实验设计空间。

BrainPEC 本文涵盖编码、使用与可解释性能三个问题，但第一个试点可以只选择其中一个。若只做编码探测，报告的 taste 测量范围就是问题操作化、实验选择、对照与结论边界，不声称已经测量所有科研能力。

### 12.5 暂不做第二点 但需要哪些最小改动

用户本轮明确跳过通用 Scientific Experiment Harness 扩建。允许的改动仅为 B 所需的接入与对照：

- 新增独立任务的题面、数据/权重入口与允许编辑范围，不修改正在运行的 REVE 任务。
- 复用 driver、attempt、job、代码快照和日志；必要时增加研究任务可选的策略入口。
- 保存假设、计划、实验选择理由、可观察的工具调用、结果、结论和人工干预，不要求或伪称拿到模型内部思维。
- 增加 skill 加载开关和版本记录，固定同一套基础工具。
- 将最终参考主张评分放在受测 Agent 之外，避免它通过反复查询隐藏答案匹配分数试探答案。

旧快照中 PROGRAM.md 按主指标决定 keep/discard，evaluation.py 需要数值指标并汇总；这套机制不能直接充当科学判断质量评分。负结果如果排除了假设，也应可作为有价值的证据保留。首次适配要核查新上游是否已有非优化型研究任务支持。

旧 PROGRAM.md 默认阅读共享知识/记忆并进行文献检索，这会和隐藏源论文的评测要求冲突。需要限定本题的信息访问与任务策略，不可只改一句任务提示就声称完成盲测。若需修改公共规则，应通过可选研究任务模式保持兼容，明确记录改动，不私下使同一个基线在两组具有不同规则。

可先采用任务旁的评分脚本和受控输入目录；没有必要为此重写整个平台。最低工具接入仍耗费工程时间，不能承诺“完全零代码改动”。

### 12.6 如何审核以及什么叫 taste 改善

FIRE-Bench 第 3.3 节侧重结论主张与论文参考发现的匹配，报告 claim-level precision、recall 和 F1。第一版 EEG pilot 可以人工复核少量主张；过程评分是我们为技能改进增加的测量层，不应冒称其原有指标已经充分衡量 taste。

| 维度 | 检查什么 | 不应替代它的指标 |
| --- | --- | --- |
| 发现覆盖 | 恢复哪些参考发现、遗漏哪些，方向/条件是否正确 | 完全一致的小数点数值 |
| 证据有效性 | 数据和权重真实、程序跑过、划分合理、分析可重做 | 报告写得像论文 |
| 实验选择 | 是否区分竞争解释，是否选择有判别力且预算可承受的实验 | 更复杂模型或更多尝试 |
| 结果解释 | 能否区分未检出与不存在、相关与使用，是否承认不确定性 | 结论更大胆 |
| 研究调整 | 根据结果继续、改方向或停止是否合理 | 必须一直改架构 |
| 资源与干预 | 时间、token、计算量和人工提示 | 单看成功次数 |

T_dev/T_holdout 的通用评价维度提前定义；具体参考答案仅构建者持有。保存每项打分的产物或轨迹位置。不要看完 skill 组结果后改权重或追加更容易得分的条目。

参考发现和其他有效结论分开记录。FIRE-Bench 第 5.2 节也讨论了合理但不对齐原论文的 Alternative 情况；不能仅因 Agent 没有走原作者路线就断言其科学推理错误。出现与原文不同的结果，先检查条件差异与证据，再决定是错误、未复现、不可比或值得后续检验的新发现。

Example skill：在一个表征指标支持某种信息存在时，先明确“可读出”和“下游使用”是不同主张；选择能够区分当前竞争解释的下一项实验，列出必要对照，在证据不足时降低结论强度。技能可以包含可迁移的方法原则，但不能包含预留题目的答案或针对该题的完整处方。

这涉及 scientific taste 的一部分：问题操作化、实验选择、证据判断、研究调整。由外部给定研究题目时，不能同时宣称检验了自主选择重要课题的能力。

### 12.7 如何检验第三点而避免自我证明

- 两组在同一个 T_holdout 上比较；不能把 T_dev 的无 skill 结果和另一题的有 skill 结果直接相减。
- 保持 agent 模型/版本、基础提示、工具、数据、预算与人工干预条件一致；两组各使用新会话和独立干净记忆。
- skill_v1 在接触 T_holdout 运行结果前冻结。记录其确实进入实际 Agent 输入，而不只保存 skill 文件。
- 同一题重新运行用于调试；同论文内换一个未用的问题只支持近迁移；不同论文/数据上的保留任务才支持更广的迁移主张。
- 如果阅读整篇 BrainPEC 后提炼了 skill，就不能把该论文其他结论称为完全未见的知识。可作为有限设置演示，正式跨论文检验需另留未用于技能开发的来源。
- 第一轮可先做每组一次的配对可行性比较，完整保留轨迹；它不提供稳定统计结论。后续扩展重复次数/题目数，并考虑同长度通用研究清单对照。
- 修改工具、换更强模型、增加预算和加 skill 如果同时发生，只能称整套系统变化；不能把全部提升归因于 skill。
- 人工辅助提炼是有效的研究开发阶段，但不是自主 RSI。后续若形成“运行经验→系统更新技能→新任务评估→保留或回退”的多轮闭环，才可研究其递归性和持续改善。
- EEG 数据的 train/val/test 划分与研究任务的 T_dev/T_holdout 是两层独立隔离：前者约束 EEG 实验，后者约束科研能力评估。

### 12.8 成果与下一次汇报的尺度

正式目标：一个可执行的 FIRE-Bench 式 EEG 任务，agent_v0 的真实轨迹与评分，一份依据失败/论文提炼的 skill，以及预算允许时的预留任务初步对照。

| 达到的进度 | 可以报告的成果 | 暂不能声称 |
| --- | --- | --- |
| 只有准备和题包 | 环境可运行、任务与评价协议已具体化 | Agent 已有科研改进 |
| 题包加真实基线 | 首个任务实例和基线；定位一个有证据的研究失败点或能力边界 | 已有完整领域 benchmark |
| 再有 skill 与预留题对照 | 某种科研策略干预的初步有效性或无效性证据 | 已稳定提高广泛 scientific taste |
| 多任务重复及多轮更新 | 可逐步评估迁移、稳健性与迭代改善 | 不经评估就等同通用科学家 |

“做不出与论文相同的结论”不自动等于有价值的负结果：要先证明资源可用、题目有效且基线运行可审计。若只有网络/缺文件阻塞，应如实作为工程进度汇报，不包装成科研发现。

目前未有数据/匹配 checkpoint 的远端可用性与用户可投入时间，不能保证下次汇报完成全部 B1–B7。优先完成题包、一次真实基线和依据明确的技能；不要为凑齐结果自动启动大规模微调。技能迁移对照可作为后续一个小步骤，而不是无限扩展平台的理由。
